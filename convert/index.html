1. Upload PDF, Page Images, or Import from URL

A single PDF, or select multiple page-image files (JPG/PNG/WEBP) at once — pick them in reading order, since the order you select them in is the order they'll be OCR'd in. JP2 isn't supported yet (no browser can decode it without an extra library) — convert to JPG/PNG first.

⚠ Keep this tab open and in the foreground while OCR/Proofread are running. Two separate things can interrupt a run: (1) mobile browsers pause a backgrounded tab's JavaScript immediately (switching apps, locking the screen) — work simply pauses and continues when you come back; (2) after a few minutes away, the browser can go further and reclaim the whole tab's memory, which wipes the live PDF file (not something any web page can prevent — it's the same browser security boundary that stops any site from reading files without you re-picking them). Either way, no OCR/Proofread progress is lost — it's saved after every single page/chunk. If Run OCR says a file needs re-selecting, that's case (2): tap "Choose Files" and pick the same PDF again — it resumes exactly where it left off. Proofread never needs this (it only reads already-saved OCR text), which is why it can resume with one tap while OCR needs the file back first.

2. Run OCR

Leave blank to OCR every page (default). Narrowing this also scopes step 3 (Proofread) to the same pages — useful for testing a few pages first, or re-running just the ones that failed, without redoing the whole book.

"Tesseract.js only" lets you preview/download a free OCR pass — e.g. to sanity-check a file — without spending any Vision quota. "Both" runs Vision as the primary result and flags pages where Tesseract disagrees, roughly doubling per-page time and downloading a language model the first time (a few MB, cached after). Tesseract requires a matching language hint above (it can't auto-detect script like Vision can) — running it with none set is refused rather than silently guessing English.

Sends this many pages in one Vision request instead of one call per page — real time savings on a large book, since it cuts the number of network round-trips, not how fast Vision reads any single page. Default 5. Set to 1 to go back to one call per page (e.g. if a single flaky page keeps taking a whole batch down — a batch fails as a unit, same "everything before it stays saved" resume as before, just a coarser unit). Only applies to "Vision AI only" — Tesseract runs locally with no network call to batch, and "Both" needs each page's cross-check done individually anyway.

Vision groups text into layout blocks and can print a whole page's worth of margin verse-numbers (॥१॥ ॥२॥ …) together at the end instead of after each verse, when they sit in their own visual column. This re-sorts the same words by on-page row position instead of trusting Vision's block order — try it if your output looks like that. Off by default (Vision's own order is usually right for plain running text).

3. Proofread

Telling Gemini what the text actually is helps it resolve ambiguous OCR errors using real context instead of guessing blind — e.g. it can favor a term that fits the known verse/commentary over a similar-looking misread. Optional; leave blank for the same behavior as before.

Large books are sent to Gemini in chunks of this many pages, not all at once — smaller chunks are less likely to hit an output limit or produce malformed JSON. Default 8; lower it if a chunk keeps failing. If you're hitting a per-request quota limit instead, try RAISING this — fewer, bigger requests use up that quota more slowly.

When on (default), a chunk is cut early — before it hits the size above — whenever a page starts a new chapter (detects "अथ <ordinal> सर्गः"-style openers), so one Gemini call never mixes the tail of one chapter with the head of the next. A real, generic contributor to boundary confusion (duplicated/dropped verses right at a chapter transition) that this removes for any chaptered text, whatever the chapter word is. Never produces a WORSE split than plain fixed-size chunking — chunks near a boundary just come out a bit smaller. Turn off only to force literal fixed-size chunking (e.g. while debugging).

Raise this if a chunk fails with "response was cut off before finishing (hit the output token limit)" — a dense commentary page's full corrected text plus per-shloka classification/notes can genuinely need more room than the old fixed default (2048) allowed. Default 8192; try 16000+ if it still gets cut off on the same chunk (or lower the chunk size above instead — either fixes it, pick whichever suits the book).
