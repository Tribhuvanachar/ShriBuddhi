⌂ DGE › 🗺️ Content Provenance · super-admin

A map of where each part of the reader-facing site actually gets its words and data from, for whoever is asked "where do I change this?" and doesn't already know this codebase's content-vs-config split. Each row points at the same file the admin editors already read and write — this page doesn't invent a second mapping, it just writes the existing one down in one place.

Scope, stated plainly: this is a static reference — a list of sources and what governs them — not a live per-element inspector that could tell you "this exact paragraph on screen comes from line N of file X" by clicking it. That would be a materially bigger feature (finding and tracing the render path of an arbitrary DOM node at runtime), and wasn't what was asked for. If a live inspector turns out to be what's actually wanted, that's a separate, larger pass — flagging the distinction here rather than quietly building the smaller thing and calling it done.

1. Page-chrome text — edited in place via the ci-bar

Titles, panel copy, labels — anything with a data-edit="dotted.path" attribute on a page whose <body> carries data-content-file="admin/content/<file>". js/content-inline.js reads and writes these; its edit toolbar (the "ci-bar") names the file it's editing whenever you click a highlighted field, so this table restates what it already tells you in one place rather than requiring a click per field.

2. Grantha corpus data — edited via the structural shloka editor

The actual texts: every data/**/data.json file, catalogued by data/library.json (one entry per grantha — path, populated, title, addedAt, optional source/facets/hidden). This is a deliberately separate editing surface from Section 1 above — js/content-editor.js (reusing admin-editor.js's commit machinery) reorders/inserts/deletes shlokas through its own structural popup, so a UI-copy edit can never accidentally go through the shloka save path or vice versa. library.json's populated flag is also what tools/build_sitemap.py reads to decide which granthas are offered to search engines — an unpopulated or admin-hidden entry is invisible to readers and is excluded from the sitemap the same way.

FileGovernsEdited via
data/library.jsonThe catalogue: which granthas exist, whether each is populated/hidden, when it was added.admin/library.html (curation), direct commits (ingestion)
data/**/data.jsonThe shloka/verse text itself, per grantha.js/content-editor.js's structural editor
admin/config/library-overrides.jsonNon-destructive display layer over the catalogue — hide a path prefix, pin, reorder, rename, move — without touching the underlying data.Exported by admin/library.html

Worth calling out on its own: content that looks editable but isn't, because it was never moved into an admin/content/*.json file.
